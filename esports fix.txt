# Antigravity Prompt — Fix Hero Section Scroll Lag (Remove Excess will-change)

> **Goal:** The 8Bit Creatives landing page has severe scroll lag in the hero section after a recent change ("move image slightly down"). The page feels janky and then suddenly jumps to the next section. Root cause: **too many `will-change` CSS properties** creating 100+ GPU compositing layers that overwhelm the browser's compositor on every scroll frame.
>
> **Fix:** Remove `will-change` from elements that don't need permanent GPU promotion. Keep it ONLY on elements with continuous CSS keyframe animations. Zero visual change — `will-change` only affects how the browser renders the element internally, not how it looks.

## Why this fix works (and is 100% safe)

### What `will-change` does
`will-change: transform` tells the browser: "I'm going to animate this element — promote it to its own GPU compositing layer NOW so the animation is smooth." This is useful for elements with CONTINUOUS animations (infinite CSS keyframes, infinite GSAP loops).

### The problem
When 20 CSS rules (some applying to 100+ elements) ALL have `will-change`, the browser creates 100+ GPU layers. Each layer uses GPU memory and requires compositing work on every frame. When the user scrolls, the GPU compositor has to:
1. Composite 100+ layers
2. Re-rasterize layers with filters (blur, drop-shadow)
3. Handle 28 backdrop-filter blur layers
4. Handle GSAP animations (parallax, float, entrance)
5. Handle CSS animations (8BIT columns, eclipse, marquee)

This overwhelms the GPU → frame drops → Lenis can't keep up → "suddenly scrolls to next section."

### The fix
Removing `will-change` from elements that DON'T need permanent GPU promotion:
- Elements with ONE-TIME entrance animations (GSAP `.from()` with no `repeat`) — GSAP sets `will-change` internally during the tween, then removes it. The permanent CSS `will-change` is redundant.
- Elements that are only animated on hover/interaction — CSS `transition` handles GPU promotion during the transition.
- DEAD CODE selectors (`.eclipse-characters .character`) — match nothing, but the browser still evaluates them.

After the fix, the GPU compositor only has to handle ~20 layers (the 8BIT columns + eclipse + marquee + canvas-container + logo + navbar) instead of 100+. The scroll becomes smooth again.

### Zero visual impact
- `will-change` ONLY affects how the browser RENDERS the element internally (GPU compositing)
- It does NOT affect the element's appearance, size, color, position, or animation
- The GSAP animations still run identically (GSAP manages its own GPU promotion during tweens)
- The CSS `transition` properties still work identically (the browser promotes to GPU during the transition)
- The `filter: blur()` and `filter: drop-shadow()` still render identically (they force GPU layers regardless of `will-change`)
